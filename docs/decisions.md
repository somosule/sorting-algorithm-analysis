**Report link:** decisions marked *Report* feed the implementation section (report Section 2: "implementation choices", brief Section 4.1 asks us to state them) or the dataset section (Section 3).

Format:

```
## Dxx: Short title
**Decision:** what was agreed.
**Why:** the reason.
**Report:** what the report must say, if anything.
```

## D01: housing.csv committed in the repository root
**Decision:** `housing.csv` sits next to `main.py` and is committed.
**Why:** The brief says to place it in the same folder as the code. Committing it (1.4 MB) means everyone uses the identical file. The README still gives the download link.
**Report:** Source URL and that the file is included.

## D02: Seed 42 for every random step
**Decision:** `SEED = 42` in `src/config.py`. Each random step creates a fresh `random.Random(SEED)`.
**Why:** Reproducibility (brief Section 7): the same samples and orders on every run and computer. Because of this, the 2,000-value sample is identical in scaling (n = 2,000), input order (before reshuffling) and repeated values (median_income).
**Report:** State the seed, how samples and orders were generated, and that all 2,000-value experiments share the same sample; only the input-order random version is reshuffled.

## D03: Sample sizes, and n = 2,000 for 4.3 and 4.4
**Decision:** Scaling: 5, 10, 20, 250, 500, 1,000, 2,000, 4,000 (50 and 100 proposed in D19). Input order and repeated values: n = 2,000.
**Why:** Small sizes support the "n < 20" decision-guide row. n = 2,000 is above the brief's minimum of 1,000 and large enough that input order clearly matters (bubble comparisons range from 1,999 to about 2 million), while all twelve algorithm and order combinations finish in seconds. 4.4 must use the same size as 4.3.
**Report:** List the sizes and explain the choice of 2,000 in one or two sentences.

## D04: Sort values only, not full records
**Decision:** The experiments sort a list of floats from one column. Full rows are never reordered.
**Why:** Brief Section 3, step 4. Keeps counting rules simple and identical to other groups.
**Report:** One sentence.

## D05: total_bedrooms not used in the experiments; optional ratio-based cleaning
**Decision:** total_bedrooms is not used in the experiments. Blank or non-numeric values are counted as missing and skipped. The dataset profile reports total_bedrooms (207 blanks) as the "before" picture. Optional side analysis (`src/missing_values.py`, decided at the Thu 5 Nov go/no-go): estimate each blank as that row's total_rooms x the median bedrooms-per-room ratio for its ocean_proximity group (<1H OCEAN 0.2067, INLAND 0.1983, NEAR OCEAN 0.2071, NEAR BAY 0.2067), then report the statistics after. housing.csv is never changed.
**Why:** Not required (brief Section 3, step 3). Forward or back fill would be wrong because rows are independent census block groups, not a time series; a single median (435) would create 207 identical values. total_bedrooms is closely related to total_rooms (correlation 0.93) and households (0.98).
**Report:** Section 3: a short paragraph on missing values and, if done, the before-and-after table; otherwise one sentence in limitations.

## D06: Counting choices beyond Section 4.1
**Decision:**
- The initial copy of the input is not counted as writes.
- Merge sort leftovers placed into the output count as writes; there is no copy-back step (unlike the zyBook version); slicing is not counted.
- A comparison counts whether it is true or false.
- Bubble sort passes shorten by one each time, as well as stopping early.
- Selection sort uses strict `<` (keeps the first minimum); bubble sort uses strict `>`, so equal values are never swapped.
- Merge sort is top-down and recursive, uses `<=`, and has 0 swaps.
- Swaps are reported separately.
**Why:** Section 4.1 asks us to state additional implementation choices; these affect the counts.
**Report:** State each choice in the implementation section.

## D07: Duplication statistic definitions
**Decision:** "Values that occur more than once" = number of distinct values with a count above 1. We also report the total entries belonging to those values.
**Why:** The brief's wording can be read two ways; reporting both avoids ambiguity.
**Report:** State the definition with the 4.4 table.

## D08: Optional record lookup extension
**Decision:** `src/record_lookup.py` sorts row numbers using a column as the key, so original records can be looked up. Public: `top_records`; private: `_load_rows`, `_merge_sort_indices` (our own merge logic, no `sorted()`). Off by default (`RUN_RECORD_LOOKUP = False`), and run after the timed experiments only. Used only if the Thu 5 Nov go/no-go allows.
**Why:** Useful for reporting individual records; merge sort with `<=` keeps equal values in their original order (stability). Not part of the required experiments.
**Report:** Mention only if used, and explain the key-based implementation (brief Section 3, step 4). It also shows median_income is capped at 15.0001.

## D09: Bubble and selection sort also count passes
**Decision:** The stats dictionary is `{comparisons, writes, swaps, passes}`. Bubble sort adds 1 at the start of every pass, including the final pass with no swaps (already sorted data gives 1). Selection sort counts its outer loop the same way (always n - 1). Merge sort reports 0.
**Why:** An extra count beyond the brief that gives direct evidence for Q6, Q10, Q11 and Q13. At n = 2,000: sorted 1 pass, nearly sorted 1,542, random 1,971, reverse 1,999.
**Report:** State that passes is an additional count, and use it in the Q11 answer.

## D10: Lean results files plus results/run_info.csv
**Decision:** Each results file contains only columns that change. scaling.csv: n, algorithm, comparisons, writes, swaps, passes, median_runtime_s, loop_reps. input_order.csv: order, algorithm, comparisons, writes, swaps, passes, median_runtime_s. repeated_values.csv: column, algorithm, comparisons, writes, swaps, passes, median_runtime_s, distinct_values, most_frequent_count, values_repeated, elements_in_repeats (D07), equal_pairs (D20). full_size.csv: algorithm, source, comparisons, writes, swaps, passes, runtime_s, runs (D16). Fixed settings (seed, runs, sample size, column) plus Python version, computer and date are written once to `results/run_info.csv`. Column lists live in `config.py`.
**Why:** Efficient and clearly labelled: no column repeats the same value on every row, and the run details are recorded in one place.
**Report:** Describe the results files briefly; quote run_info.csv for the machine and Python version.

## D13: Public functions and private helpers
**Decision:** Functions used by other files are public, keep their agreed names and are never renamed. Helpers used only inside one file start with `_`. No file calls another file's `_` functions; tests call only public functions.
**Why:** Each file shows a small, clear set of functions; private helpers can change without breaking others. Python does not enforce this, so reviewers check it.
**Report:** Optional one sentence in the design description (key subroutines).

## D14: Loader behaviour
**Decision:** `load_rows()` returns every row exactly as read, blanks included. `load_column()` counts blank or non-numeric values as missing and skips them, and raises `KeyError` if the column does not exist (so a typo cannot silently give empty results). A missing file raises `FileNotFoundError` pointing to the README.
**Why:** Keeps the raw data intact for the profile and the optional cleaning, and makes mistakes fail loudly.
**Report:** One sentence on input preparation and error handling.

## D15: Optional selection sort estimate and bubble sort check
**Decision:** Optional: estimate selection sort for 20,640 values the same way as bubble sort (calculation only), and run bubble sort once on all 20,640 values only after its estimate is saved, as a check (`RUN_BUBBLE_FULL`, off by default). Run once on the official machine (D11). The merge sort full-size run is no longer optional (D16).
**Why:** Brief 4.2 step 4 allows the bubble check only after the estimate.
**Report:** If done, a small table in Section 4 (estimated vs measured), with the bubble estimate's % difference.

## D16: Merge sort measured on all 20,640 values (standard)
**Decision:** `run_full_size()` in experiments.py runs merge sort on all 20,640 median_income values in the order given by `random.Random(42).sample(values, 20640)`, the same `sample()` call as every other experiment (not `shuffle()`, which gives a different order and 270,271 comparisons) (5 runs, median), on every run of main.py (called after the bubble estimate, D21), and saves `results/full_size.csv` (algorithm, source, comparisons, writes, swaps, passes, runtime_s, runs). Expected: 269,952 comparisons and 297,472 writes.
**Why:** Our largest scaling sample is 4,000, so without this the decision guide's "Large random input" row would rest on n = 4,000 and an estimate. Merge sort at full size takes under a second, so a real measurement costs nothing.
**Report:** Cite it in the decision guide (Section 7) and next to the bubble estimate in Q4.

## D17: Decision-guide evidence generated by code
**Decision:** `make_plots()` also writes `results/tables/decision_guide_evidence.csv` with the numbers each of the six decision-guide rows needs (situation, source, n, algorithm, comparisons, writes, passes, median_runtime_s, fastest). The decision guide's evidence column is taken only from this file. For "Many repeated values", the Why reuses the Q12 split so only differences caused by duplication are credited to duplication; writes are the tie-breaker when times are close.
**Why:** No hand-copied numbers, so the table always matches the official run and the number check (H9) is quick. Brief 4.5 requires measurements as evidence, not Big-O alone.
**Report:** Section 7 decision guide; mention that the evidence numbers come from the final run's results files.

## D18: What "best-performing" means
**Decision:** In Q9 and the decision guide, the best algorithm is the one with the lowest median runtime in our results. Comparisons, writes and passes explain why it won. If two runtimes are within about 10%, we call it close and use writes as the tie-breaker.
**Why:** The brief asks for the best performer "based on your measurements"; runtime is what a user experiences, and the counts make the explanation independent of the machine.
**Report:** State the definition once, before the Q9 answers and the decision guide.

## D19: Scaling sizes 50 and 100 added
**Decision:** `SCALING_SIZES` becomes (5, 10, 20, 50, 100, 250, 500, 1000, 2000, 4000): 30 rows in scaling.csv. `SMALL_N_MAX` stays 20, so n = 50 and 100 are timed with single calls (median of 5). Growth factors still use the doublings from 250 upwards.
**Why:** Without them the sizes jump from 20 to 250, so Q5 could only say merge sort overtakes "somewhere between 20 and 250". Trial runs put the crossover at about n = 20 against bubble sort and between 20 and 50 against selection sort. The extra sizes cost a fraction of a second.
**Report:** Q1 (sizes used and why) and Q5.

## D20: Equal pairs recorded for the repeated-values experiment
**Decision:** `duplication_stats()` also returns `equal_pairs` (pairs of equal values), saved as a column in repeated_values.csv. The repeated-values table also shows the bubble swaps a random arrangement would give, (n(n - 1)/2 - equal_pairs) / 2, and the difference from the actual swaps.
**Why:** Bubble sort swaps once per out-of-order pair and never for equal values, so this separates the duplication effect from the order effect with numbers (Q12). Expected: housing_median_age's duplicates should cut about 25,000 swaps, but its arrangement added about 17,000; reshuffling the same median_income values alone changes swaps by about 20,700.
**Report:** Q12 and the decision guide's "Many repeated values" row.

## D21: main.py call order
**Decision:** main.py runs profile_dataset, run_scaling, run_input_order, run_repeated_values, write_growth_factors, write_bubble_estimate, run_full_size, then make_plots.
**Why:** The brief allows the full bubble sort run only as a check after the estimate has been made, so run_full_size (which holds the optional check) comes after write_bubble_estimate. make_plots comes last because the decision-guide evidence table needs full_size.csv.
**Report:** The design-flow diagram follows this order.

## D22: Two statements for the implementation section
**Decision:** The report states that (a) statistics.median, used only on the 5 timing values in measure.py, sorts those 5 numbers internally and never touches the housing data; and (b) each sort's first step copies the input, which is inside the timer but not counted as writes, and is the same for all three sorts.
**Why:** The brief bans sorted() for processing the data and asks us to state additional implementation choices; saying this up front stops a reader from thinking either rule was broken.
**Report:** One or two sentences in Section 2.
